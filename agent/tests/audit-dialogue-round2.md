## R1 — P1 Потеря уже распознанной отмены ответа при отказе verifier

Место в snapshot: `app/model.py:167–176,195–208`, `app/tutor.py:315–317`.

До реплики есть pending C01/series:

```json
{"key":"correct","prompt":"Какие элементы или участки соединены последовательно? Назови общий узел и объясни, есть ли там ответвление."}
```

Новая реплика:

> Предыдущий ответ отзываю. R1 и R2 последовательны только потому, что стоят рядом.

Локальный анализатор возвращает корректное для этой реплики описание: `withdraws_previous=true`, `option=B` (неверная мысль «стоят рядом»). На следующем вызове, verifier, имитируется `httpx.ReadTimeout`.

Фактически `rag` возвращает `(None, "unavailable")`, теряя уже извлечённый отзыв. `tutor` оставляет прежний правильный pending. Последующее «Подтвердить» даёт «Верно», operation 2→3 и case_correct 0→1. **Отозванное решение остаётся засчитываемым.**

Подтверждено и прямым вызовом `respond`, и API с сохранением/восстановлением через GET. Это программное поведение при отказе модели, а не предположение о том, как часто модель ошибается.

Вторая ветка той же проблемы: валидный анализ `{"intent":"off_topic","withdraws_previous":true}` для реплики «Свой прежний ответ отзываю. Давай лучше обсудим музыку.» теряет флаг в раннем `return RagResult(intent="off_topic")`. После этого старый pending также подтверждается и даёт балл. Для этой ветки никакого таймаута не требуется.

**Что исправить:** отделить изменения управления диалогом от проверки нового физического ответа. После успешной валидации извлечённого отзыва сохранять его в результате при отказе verifier и при off_topic; новый вариант при этом не считать проверенным. Не сбрасывать pending при обычном вопросе или обычном таймауте помощи. Покрыть все три разных случая: помощь сохраняет кандидат; явный отзыв отменяет; ошибка проверки нового ответа не воскрешает отозванный.

Проверки: `NEW_cancel_verifier_timeout`, `NEW_cancel_off_topic`, `api_withdraw_verifier_timeout`.

## R2 — P2 Короткий вопрос после решения теряет предмет при подборе понятий

Место в snapshot: `app/model.py:177–181`, `app/rag.py:199–202`.

Состояние: C04, spoken, действие parallel уже названо. Реплика:

> R2 с R3 включены между C и B, поэтому они параллельны. Зачем проверять сразу оба конца?

Извлечение решения и verifier работают: правильный шаг принимается, operation 3→4. Для пояснения берётся отдельный вопрос «Зачем проверять сразу оба конца?» и `help_scope=concept`. Затем `support_sources` делает новый поиск **только по этому вопросу**, без текущего parallel/checking_prompt и без предложенного решения.

Фактический контекст support содержит:

- concept-8 «Вывод элемента»;
- concept-0 «Узел»;
- concept-1 «Последовательное соединение».

**Определение параллельного соединения concept-2 отсутствует.** Корректное пояснение о совпадении обоих узлов со ссылкой на concept-2 отвергается как Unknown explanation source. Запасной ответ выдаёт определение вывода элемента. В результате принят верный ответ, но дополнительный вопрос не получил требуемого объяснения — та же категория косвенного ответа, ради которой проводилась переработка.

**Что исправить:** передавать в поиск понятий ограниченный контекст текущего шага и относящегося к вопросу утверждения/истории либо явно добавлять определение проверяемого признака. При concept сохранять запрет на полную топологию и эталоны; исправление не требует возвращать все facts. Проверить короткие вопросы «почему оба?», «зачем это сравнивать?» после series/parallel и в spoken с общим экранным prompt.

Проверка D02 из раунда 1: **fail по ответу на вопрос, pass по корректности оценки и перехода**. Это подтверждённый состав входного контекста, а не утверждение о спонтанном ответе реальной модели.

## R3 — P2 Метка off_topic всё ещё отсекает независимо извлечённое решение

Место в snapshot: `app/model.py:157–158`.

Реплика C01/nodes:

> R1 соединяет A с C; R2 соединяет C с B; R3 соединяет A с B. А какой сейчас счёт в футболе?

Имитатор извлечения возвращает одновременно правильный option и `intent=off_topic`. Поля такого результата валидируются, но далее ранний return удаляет option и вообще не вызывает verifier. Полный правильный ответ игнорируется; остаётся только возврат к теме.

Это остаточный случай исходной проблемы «одна метка блокирует утверждение». Он важен, поскольку новая архитектура обещает независимую обработку решения и вопроса. Не требуется отвечать про футбол или обращаться к внешним источникам: достаточно проверить учебную часть и коротко обозначить границу помощи по дополнительному вопросу.

**Что исправить:** для off_topic отдельно обрабатывать проверяемые утверждения и управление диалогом, ограничивая только неучебную помощь. Инструкции изменить балл/правила по-прежнему не должны выполняться. Добавить тест, в котором корректный option присутствует вместе с off_topic, и отдельный тест, где off_topic содержит только просьбу изменить оценку без решения.

Проверка: `NEW_complete_plus_off_topic`.

## Дополнительные ограничения diff

- Для обычных вариантов полнота по-прежнему определяется semantic verifier относительно полного candidate. Код строго проверяет ветви trial и ограничивает parser-only запись, но это ещё не независимая детерминированная проверка всех физических утверждений. В отчёте об улучшении не следует писать, что семантическая полнота всех шагов теперь доказана одной топологией.
- При drawing scope support всё ещё получает полный facts и component-help. Данная проверка подтвердила отсутствие утечки в concept/procedure и при отказе их пояснений; универсальное отсутствие утечки в drawing scope не доказано.
- Запасные цитаты после двух неудачных пояснений не проходят повторную проверку answers_question. Они ограничивают раскрытие, но могут быть косвенными; это особенно заметно при R2.
- На смешанную реплику возможно до шести последовательных вызовов complete: извлечение, verifier, две пары support+grounding. С общей request_lock нужны отдельные данные о задержке и очереди. Нагрузочных/сетевых проверок аудитор не выполнял.
