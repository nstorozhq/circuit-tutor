## Оценка гипотез

1. **Одна метка intent блокирует смешанную реплику — подтверждено.** В исходном `model.py:108–129` сначала выбирается одна категория. Для `question/partial/clarify` не вызывается извлечение ответа. Затем `validate_result` в `rag.py:212–214` удаляет `option` и `branches` для любого intent, кроме answer. `tutor.py:298` может вернуть помощь раньше обработки решения. Утверждения и вопрос нужно представлять независимо; наличие вопросительного знака не должно уничтожать утверждение в другой части реплики.
2. **Router не может надёжно определить полноту без текущей задачи и топологии — подтверждено ограничением входа.** В исходном payload router нет ни состава схемы, ни подключений, ни списка требуемых признаков. Полноту следует вычислять по извлечённым утверждениям и требованиям конкретного шага. Истинное частное утверждение не равно полному решению.
3. **Grounding не гарантирует ответа на вопрос — подтверждено.** В исходном `model.py:142–144` проверке передаются только explanation и sources, без вопроса ученика. Истинный пересказ схемы проходит, даже если не отвечает на вопрос о повороте рисунка.
4. **Support получает лишний эталон — подтверждено, причём удаление одного источника недостаточно.** `retrieve` добавляет `C01-facts` со всеми подключениями. При некоторых вопросах добавляется ещё `C01-nodes`. Даже когда отдельный reference исключён, facts и component-help могут полностью содержать искомый результат. Для подсказки нужна отдельная политика доступных сведений и допустимого раскрытия.
5. **Дополнительный риск: локальный быстрый путь обходит семантическую проверку.** Правильные пары узлов вместе с противоречащим им общим утверждением принимаются детерминированно. Новый анализ смешанных реплик должен охватывать и этот путь.
6. **Дополнительный риск: incomplete превращается в правильный ответ через простое подтверждение.** В исходной реализации verifier=incomplete вызывает предложение полного правильного эталона; bare «Подтвердить» затем даёт балл. Нужно различать подтверждение распознавания уже высказанного решения и предложение недостающего обоснования за ученика. Если продукт сознательно допускает второй путь, результат должен помечаться как выполненный с помощью и не свидетельствовать о самостоятельном выполнении.

## Общие критерии новых проверок

- Фиксировать до и после: `phase`, `index/case_id`, `operation`, **полный pending**, `spoken_named`, `case_correct`, `scores`, `errors`, `assisted`, `revealed`, `show_options`. Поля журналирования и версия API могут меняться при сохранении сообщения.
- Для помощи без нового решения не менять этап, операцию, счёт и сохранённый кандидат. Допустимо пометить помощь; подсказка может увеличить счётчик подсказок. Ошибка или штраф не должны появляться за сам вопрос.
- Подтверждение после помощи относится к тому же `case_id`, шагу и кандидату. Равенство одного boolean `pending=true` этого не доказывает. В исходном JSON полный pending не записан.
- Смешанную реплику проверять по двум результатам: обработано ли её утверждение и получен ли ответ на вопрос. Истинный пересказ схемы вместо ответа — отдельный провал.
- Успех не должен требовать буквального совпадения с эталонным текстом. Полнота — все требуемые признаки текущего шага, отсутствие неотменённых противоречий и корректная область утверждения: элемент, ветвь или вся схема.
- Вопрос-гипотеза без утверждения решения не засчитывается. Вежливость, благодарность или отдельный уточняющий вопрос не отменяют явно высказанный ответ. Неоднозначность уточняется, а не разрешается за ученика.
- Для определения или подсказки запрещён не весь физический факт вообще, а выдача полного ответа текущей задачи вместо запрошенной помощи. Явная команда «Покажи ответ» имеет другую политику и должна сохранять отметку раскрытия.
- Имитатор проверяет устойчивость к допустимым ошибкам модели. Живой прогон, если отдельно разрешён, проверяет качество модели; его результаты нельзя заменять успешными тестами с готовыми структурами.

## Контракты и проверки ошибочных результатов модели

Новый формат должен позволять выразить утверждения и вопрос одновременно; конкретные имена полей не предписываются. Для diff нужны проверки не только успешного JSON, но и следующих ответов имитатора:

1. Router/анализатор ошибочно помечает полное утверждение как partial или off_topic. Детерминированный валидатор вправе восстановить только действительно извлечённые утверждения, включая проверку противоречий.
2. Анализатор возвращает complete=true, но указал лишь один элемент C05 или один из двух требуемых общих узлов. Флаг модели не заменяет вычисление полноты по задаче.
3. Анализатор приписывает ученику отсутствующие пары/обоснование, копируя их из sources. В зачёт попадают только высказывания ученика или явно разрешённые ссылки на его прежние высказывания с происхождением.
4. Grounding возвращает supported для истинного, но нерелевантного пояснения. Нужна отдельная проверка ответа на исходный вопрос; повторная проверка тех же физических фактов проблему не решает.
5. Explanation ссылается на существующий source_id, но вывод не следует из него либо игнорирует оговорку «скрыт». Идентификатор источника не является доказательством.
6. Explanation отвергнуто. Запасной ответ должен иметь ту же или более строгую границу раскрытия, что обычная помощь. Нельзя автоматически цитировать целиком первый выбранный моделью источник.
7. Существующий элемент присутствует в тексте ученика, но отсутствует в текущей схеме. Наличие токена во входе не разрешает модели считать его существующим здесь.
8. История содержит старую интерпретацию, затем её явный отзыв. Обработка нового сообщения не должна восстанавливать отозванный кандидат из recent_dialogue.
9. Невалидный JSON/неизвестный source_id/timeout во время помощи. Сохранение pending и этапа проверяется во всех ветках, включая резервный ответ.
10. Ограничение числа обращений к модели. Подсчитать worst-case число последовательных вызовов, таймаут и очередь; корректная обработка реплики не должна зависеть от скрытого повтора production-запросов или ручного очищения сессии.

## Порядок проверки готового diff
