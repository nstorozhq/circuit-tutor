## R4 — P1 Неверный вычисленный источник для составного последовательного участка

Место в snapshot: `app/rag.py`, `support_sources`, строки 238–247. Ветка series всегда добавляет фразу «Нет ответвлений в промежуточных узлах», независимо от того, являются ли участки одиночными элементами или параллельными блоками.

Для C04 генерируется источник `C04-relation-series-0`:

> Участки R1 и (R2 ∥ R3) соединены последовательно. Нет ответвлений в промежуточных узлах C.

Первое предложение корректно для целых участков; второе — неверно для узла C исходной схемы. Подключения здесь R1: A–C, R2: C–B, R3: C–B. В C сходятся три элемента, ток разветвляется между R2 и R3. Последовательное соединение R1 с параллельным блоком не означает отсутствия этого разветвления.

Уже существующий `question(CASES['C04'], 'series')['reference']` различает эти случаи правильно:

> R1 и (R2 ∥ R3) соединены последовательно. В узлах C между этими участками нет отдельной ветви.

То есть новый путь помощи потерял оговорку, которая есть в основном генераторе эталона.

Одна причина затрагивает три вычисленных источника:

| Источник | Число элементов, подключённых к C | Некорректная часть |
| --- | --- | --- |
| C04-relation-series-0 | 3: R1, R2, R3 | «Нет ответвлений ... C» |
| C09-relation-series-0 | 3: L1, L2, L3 | «Нет ответвлений ... C» |
| C11-relation-series-0 | 4: R1, R2, R3, R4 | «Нет ответвлений ... C» |

Для C09 и C11 подтверждён дефект генератора источников; выдача через обычный учебный диалог проверена именно на доступной тренировочной C04. Нельзя приписывать этим двум случаям обход блокировки контрольной или режима done: такой обход не проверен и не заявляется.

### Фактическое поведение C04

Состояние: spoken, C04, операция series, действие уже названо (`spoken_named=true`).

Вход:

> Почему R1 и целый блок R2 с R3 рассматриваются как последовательные участки?

Локальный имитатор выбирает допустимый `drawing/explain`, существующий источник `C04-relation-series-0` и возвращает положительную проверку grounding. Произвольного физического explanation имитатор не подставляет: выводимый текст полностью построен самим приложением из источника.

Фактический ответ приложения:

> Участки R1 и (R2 ∥ R3) соединены последовательно. Нет ответвлений в промежуточных узлах C.

POST и последующий GET согласованы; шаг и балл при вопросе сохраняются. **Проблема находится в физическом тексте, а не в переходах или сохранении сессии.**

Это не доказательство того, что реальная модель обязательно выберет данный источник. Подтверждено, что источник неверен и разрешён для показа как достоверный вычисленный факт. Grounding, которому этот же источник задан как основание, не является независимой проверкой корректности генератора.

### Что исправить и проверить

- Для простых последовательных цепочек сохранить корректное утверждение об отсутствии ответвлений.
- Для составных участков использовать точную формулировку основного эталона о том, что между рассматриваемыми участками нет отдельной ветви; не отрицать разветвления внутри параллельного блока.
- По возможности формировать атомарный текст и основной эталон через общий проверенный механизм, чтобы эти два представления не расходились.
- Добавить проверки C04, C09 и C11 на смысл серии составных участков; отдельно оставить простую C02 положительным примером и C06/C08 с неопределённостью скрытой связи.
- Повторить фактический путь C04 через support/API, а не ограничиваться проверкой наличия source_id.

## Остаточные ограничения новой архитектуры

- Дословная выдача исключает свободно придуманную моделью физическую фразу в explanation, что подтверждено. Она переносит ответственность за факты на KB и генератор; R4 показывает необходимость независимой проверки именно вычисленных источников.
- Выбор source_ids и yes/no по-прежнему семантически зависит от модели. Префикс «Да/Нет» тоже может изменить смысл ответа, поэтому нельзя заявлять абсолютную гарантию физической корректности только из-за дословного основного текста.
- Ограничение «не более одного атомарного факта» подтверждено как количество выбранных non-concept источников. Оно само по себе не означает, что источник не содержит полного результата текущего шага: inventory содержит весь состав схемы, relation может содержать весь ответ об одной группе. Для hint это закрывается фильтрацией; поведение drawing/explain нужно оценивать по конкретному запросу.
- Дедлайн проверен локально на настоящем complete без HTTP с короткой тестовой границей, включая очередь. Полный 35-секундный сетевой прогон и нагрузка не выполнялись.

## Предлагаемый общий контракт физических утверждений

Это проект контракта для следующей реализации, а не описание уже внесённого кода. Он не задаёт исключений для конкретных текстов D05/D06. Главное разделение: модель извлекает выраженные утверждения, сервер определяет их истинность по графу и проверяет, **что именно ученик сообщил**, а не что можно вывести из готового ответа.

### 1. Ответ модели — извлечённые утверждения, без оценки

Модель не возвращает authoritative-поля `correct`, `complete`, `equivalent`, `score` или `advance`. Пример для исходной строки `R1: A–C.`; диапазоны полуоткрытые, индексы Unicode-кодовых точек исходного student_text:

```json
{
  "schema_version": 1,
  "utterances": [
    {
      "span": {"start": 0, "end": 8},
      "kind": "assertion",
      "claim_ids": ["c1"]
    }
  ],
  "claims": [
    {
      "id": "c1",
      "predicate": "terminals",
      "subject": {"kind": "element", "id": "R1"},
      "arguments": {"nodes": ["A", "C"]},
      "quantification": {"kind": "explicit", "domain_ref": null},
      "polarity": "positive",
      "modality": "asserted",
      "evidence": [{"start": 0, "end": 7}],
      "entity_evidence": [
        {"ref": "element:R1", "span": {"start": 0, "end": 2}},
        {"ref": "node:A", "span": {"start": 4, "end": 5}},
        {"ref": "node:C", "span": {"start": 6, "end": 7}}
      ]
    }
  ],
  "questions": [],
  "retractions": [],
  "unresolved_spans": []
}
```

Реальная реализация обязана проверять каждый диапазон против исходной реплики и сохранять соответствие при нормализации обозначений. `entity_evidence` связывает каждое R1/A/C с его упоминанием или допустимой явной ссылкой в истории. Нельзя смешивать индексы Python-кодовых точек и JavaScript UTF-16 без преобразования.

Требования схемы:

- Все поля структуры обязательны; отсутствие данных выражается пустым массивом/null, а не пропущенным ключом. `additionalProperties=false` на каждом объекте, строгие enum, ограничения длины/числа записей и tagged union для аргументов каждого predicate.
- Case, версия урока, список допустимых сущностей и текущий шаг принадлежат серверу. Модель получает их для извлечения, но не может выбрать другой case/topology через свой ответ.
- `kind`: assertion/question/uncertainty/retraction/discourse/unresolved. Одна реплика может содержать несколько разных актов. Intent не управляет возможностью проверить claims.
- `modality`: asserted/proposed/hypothetical/conditional/quoted/retracted. Вопрос о правиле и цитата не становятся собственным утверждением ученика. Конкретное предложенное решение «верно?» допускает проверку истинности; вопрос без собственного решения не даёт учебного зачёта.
- `polarity` и квантор хранятся отдельно от предмета отношения. Нельзя удалять отрицания или превращать «все» в выбор удобной пары.
- Структурный этап не может заполнять отсутствующие node IDs, промежуточный узел или основание из KB. Такие факты могут быть истинны, но они не высказаны учеником.

### 2. Сущности и предикаты имеют типы

Сервер предоставляет каталог: элементы, электрические узлы, стабильные ID двухполюсных участков из дерева circuit и их внешние выводы. `element:R1` и `block:(R2∥R3)` — разные типы объектов. Названия блоков нужны как ID структуры, а не как строки с поиском круглых скобок.

| Предикат | Смысл и аргументы | Проверка сервером |
| --- | --- | --- |
| inventory/member | Какие элементы входят в рассматриваемый участок | Сравнение с серверным набором листьев; лишние/пропущенные элементы различаются |
| terminals | Пара внешних узлов элемента или блока | Неупорядоченная пара; A–C и C–A эквивалентны. Известное и неизвестное подключение различаются |
| series_chain | Указанные элементы/блоки образуют одну последовательную цепь | Проверка цепи и отсутствия **внешней дополнительной ветви между блоками**; не объявлять все её листья попарно соседними |
| parallel_group | Указанные элементы/блоки имеют общую пару внешних узлов | Пары внешних узлов совпадают и определены; один общий узел не даёт parallel |
| branch_at_node | В физическом узле есть/нет разветвление | Проверка инцидентных связей графа с учётом неизвестных связей; не смешивать с границей составного блока |
| same_terminal_pair | У всех объектов выбранного домена одна и та же пара выводов | Проверка каждой пары выводов в домене; для R1 A–C, R2 C–B, R3 A–B результат false |
| classification | Вид всего указанного участка | Вычисление по текущей структуре с учётом неизвестности, не по числу элементов или геометрии |
| drawing_position | Положение обозначенных элементов на рисунке | Отдельный графический атрибут; положение не доказывает электрическое соединение |
| rule_condition | Утверждение о необходимом/достаточном условии соединения | Сравнение с закрытым формальным правилом знания; не выводить общий закон из одного частного рисунка |

Для `series_chain` на домене из трёх элементов требуется принадлежность одной последовательной цепи, а не непосредственная общая точка у каждой из трёх пар. Это защищает корректную C02 от неверной универсализации «последовательны ⇔ все попарно соседние».

### 3. Универсальные утверждения проверяются на полном домене

Квантор должен содержать вид и область действия:

- `explicit` — явно перечисленные элементы/блоки;
- `all` — весь указанный серверный домен;
- `exists` — хотя бы один объект/группа домена;
- `none` — ни один объект/группа;
- для «только»/исключений — явная граница включения и исключения, без потери ограничителя.

Допустимые domain_ref задаёт сервер: например, `current_case.elements`, `current_task.target_blocks`, `parallel_block:b1.children`. Фраза «все три резистора» относится к трём элементам, а не к двум удобным составным ветвям. Если предмет «все ветви» неоднозначен, domain остаётся unresolved, а не подбирается до получения true.

Для D06 обязательны **четыре** активных утверждения: три terminals и одно all/same_terminal_pair на current_case.elements. Наличие трёх истинных terminals не отменяет четвёртое ложное утверждение. Оно делает полный ответ противоречивым независимо от того, верен ли выбранный candidate.

Нельзя реализовывать это правилом «если встретилось слово “все” и не встретилось “ветвь”, отклонить»: истинность зависит от типа отношения, выбранного домена и графа. Для всех параллельных элементов C07 соответствующее all-утверждение истинно, для трёх элементов C01 — ложно, для двух целых ветвей C01 — истинно.

### 4. Истинность и полнота — разные проверки

Каждое активное утверждение получает серверный результат `true/false/undetermined`. Для скрытых связей применима трёхзначная логика:

- true — утверждение верно при всех допустимых завершениях скрытой связи;
- false — неверно при всех допустимых завершениях;
- undetermined — разные допустимые завершения дают разные результаты.

Отсутствие данных не доказывает отсутствие связи. Условное утверждение проверяется вместе с явным условием и не превращается в безусловную установленную топологию. Утверждение «данных недостаточно» желательно подтверждать двумя допустимыми завершениями с разным результатом, вычисленными сервером.

Затем сервер применяет спецификацию текущего шага. Пример:

| Шаг | Что должно быть явно представлено в ответе ученика |
| --- | --- |
| trial | Каждый требуемый элемент назначен нужной ветви рисунка ровно один раз |
| elements | Весь требуемый состав без лишних элементов |
| nodes | Для каждого элемента указана нужная пара узлов либо корректно обозначена неизвестность |
| series | Нужные последовательные группы и предусмотренное заданием основание об общем узле/отсутствии отдельной внешней ветви |
| parallel | Нужные параллельные группы и **названная учеником** общая пара узлов, когда вопрос требует указать оба узла |
| overall | Общий вид и требуемые связи между найденными участками |

В D05 утверждение parallel_group может быть истинным, но A/B отсутствуют в реплике: требование назвать оба узла не покрыто. **Нельзя засчитывать полноту через логический вывод «parallel по определению означает общие A/B»**, потому что этот вывод дописывает за ученика именно то обоснование, которое проверяется.

### 5. Итоговый результат проверки задаётся сервером

```text
if extraction_invalid or unresolved_physical_spans:
    outcome = unclear
elif any(active_claim.truth == false) or unresolved_contradiction_between_claims:
    outcome = contradiction
elif any(required_task_fact lacks explicit student evidence):
    outcome = incomplete
elif any(required_claim.truth == undetermined without explicit acknowledgement):
    outcome = incomplete
else:
    outcome = complete_correct
```

Условие покрытия применяется к собственным активным утверждениям; отдельно учитываются вопросы и помощь. Не всякая дополнительная реплика должна быть ошибкой, но дополнительное ложное физическое утверждение не может быть молча проигнорировано. Явно зачёркнутые/отозванные старые утверждения удаляются из активного набора с сохранением provenance. При двух несовместимых действующих утверждениях нельзя молча выбирать последнее.

Оценка, operation и счёт меняются только по outcome, контексту этапа и серверной рубрике. LLM-verifier можно оставить диагностическим сигналом, но он не отменяет incomplete/contradiction, вычисленные по фактам. Вопрос и off_topic обрабатываются независимо от этого результата. Контрольные ограничения применяются до запроса помощи.

### 6. Происхождение и полнота извлечения — оставшаяся граница доверия

JSON Schema гарантирует форму, но не доказывает верность извлечённого смысла. Модель может вернуть три terminals и просто пропустить универсальную фразу D06. Даже идеальная проверка графа тогда проверит неполный пересказ.

Для строгого режима нужны следующие условия:

1. Каждый claim связан с минимальным диапазоном исходной реплики; текст источника и названные сущности проверяются кодом. Факт из KB не может получить provenance ученического утверждения.
2. Сервер сегментирует поддерживаемый язык утверждений на клаузы. Физические отношения, отрицания, кванторы, исключения и условия относятся к грамматике операторов, а не к списку исключений для отдельных тестовых фраз. Каждое такое употребление должно быть отражено в AST либо в unresolved_spans.
3. Необработанная физическая клауза препятствует автоматическому зачёту. Поля модели «coverage complete» или пустой unresolved-массив сами по себе этого не доказывают.
4. Приветствие/благодарность можно отделять как discourse. Неопределённую дополнительную прозу нельзя целиком объявлять discourse ради приёма полезного фрагмента.
5. Для фразы вне поддержанной грамматики безопаснее запросить конкретное недостающее утверждение либо показать извлечённые утверждения для уточнения. Это не должно выдавать отсутствующее обоснование в составе «уточнения» и затем засчитывать его одним «да».

**Предел гарантии:** на произвольном естественном языке нельзя получить доказательство полноты смысла одной JSON-схемой и повторным суждением той же модели. Детерминированный checker гарантирует проверку верно извлечённого AST. Абсолютный отказ от false positive требует ограничения поддержанного языка/структурированного ввода и осторожного уточнения вне него. Это нужно прямо учитывать при оценке false negatives original-1/D01/D02.

### 7. Проверки контракта без привязки к формулировкам

- Перестановки узлов и порядка перечисления сохраняют outcome для неполярных элементов.
- Добавление истинного, относящегося к задаче утверждения не превращает полный верный ответ в ошибочный.
- Добавление ложного активного универсального утверждения превращает полный ответ в contradiction.
- Удаление явно требуемого узла/основания превращает complete_correct в incomplete, даже если тип соединения назван правильно.
- Добавление вопроса сохраняет результат проверки уже высказанных утверждений и добавляет отдельную обязанность ответить.
- Цитирование/вопрос о ложной гипотезе не равны утверждению этой гипотезы.
- Явный отзыв ложного утверждения с полным новым решением может восстановить complete_correct; неподтверждённое «последнее выигрывает» запрещено.
- Один all-оператор проверяется на разных доменах: элементы C01, элементы C07, целые ветви C01, составные блоки C04. Ожидания выводятся из графа, а не из одинакового слова «все».
- Добавление или удаление фактов в KB/support не меняет того, что считается высказанным учеником.
- Метки intent и ответы semantic verifier не могут изменить false/incomplete, полученные серверным checker.

## Native structured output

Официальная [документация Сбера](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output) проверена read-only. Для `/v1/chat/completions` она задаёт `response_format` с `type: "json_schema"`, `schema` и `strict: true`; для `/v2` этот объект находится в `model_options.response_format`. В схеме нужен список required. Это полезная транспортная гарантия структуры; доказательство семантической полноты и истины выше является отдельным требованием к приложению.

Новая реализация structured output и предложенного checker в текущем аудите не проверена: автор объявит следующую готовую версию отдельно. Итог текущего snapshot и свидетельства живого прогона сохранены без замены.
