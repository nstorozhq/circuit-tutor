## Совместимость Python 3.10 и точность изоляции

После прежнего аудита автор обнаружил production AttributeError: серверный Python 3.10.12 не имеет `asyncio.timeout`. Локальные проверки выполнялись на Python 3.12.14 и не являлись проверкой запуска на серверном runtime. Текущий app/KB-diff относительно предыдущего manifest затрагивает **только model.py**: `asyncio.wait_for` оборачивает ожидание lock вместе с запросом; в обработчики добавлен `asyncio.TimeoutError`. Остаток общего 35-секундного бюджета сохраняется. `wait_for` доступен в [официальной документации Python 3.10](https://docs.python.org/3.10/library/asyncio-task.html#asyncio.wait_for); объединение `asyncio.TimeoutError` со встроенным `TimeoutError` произошло в [Python 3.11](https://docs.python.org/3.11/library/asyncio-exceptions.html#asyncio.TimeoutError).

Новый async unit проверяет занятый lock, отмену начатого запроса и исход `unavailable`. Старое ожидание встроенного TimeoutError в mixed-тесте исправлено на `asyncio.TimeoutError`. В test_accounts/test_lesson `TestCase.enterContext` заменён на `ExitStack` с `addCleanup`: assertions сохранены, клиент закрывается до удаления временного каталога. Эти изменения проверены read-only; app аудитор не менял. Локально независимо прошли 62/62 выбранных unit, 12/12 portable API, replay D01 и прежние согласованные пробы. Самостоятельно Python 3.10 здесь не запускался.

### API, pending и транзакции

Основной API-набор проходит через настоящий offline `GigaChat.rag → claims → tutor → API`; модельные ответы заданы заглушкой. Диагностический verifier намеренно возвращает `contradiction`. При правильных переставленных парах C–A/B–C/B–A сервер всё равно принимает проверенный графом ответ. Повторное bare confirm после использования решения не добавляет балл.

Обычный вопрос и timeout сохраняют **весь** pending, а не только его наличие. После этого подтверждение засчитывает исходное решение ровно один раз. Явный отзыв и D14 очищают pending; два последующих подтверждения не меняют операцию и балл.

В последовательных сценариях проверены равенство ответа на повторный `message_id`, согласованность POST→GET и отсутствие изменений после запроса с устаревшей версией. Число созданных аккаунтов во временных БД равно нулю.

Конкурентный откат проверен после вычисления ответа: извлечение хода с version=0 задержано; «Режим учителя» успевает сохранить version=1; задержанный правильный ответ затем получает HTTP 409. Сохранены `teacher=true`, operation=1 и `case_correct=0`, история содержит три сообщения, проигравший `message_id` отсутствует в turns. Неверный переход и балл не остаются в БД.

## Граница вывода

Проверяемый контракт — конечные типы фактов: элементы, расположение, пары выводов, отношения серии/параллели, их обоснование, отсутствие отношения, общий тип схемы, неизвестность, универсальные утверждения с доменом, название действия и отзыв. У фактов проверяется буквальное происхождение из реплики; физическая оценка не делегируется решающему semantic-verifier.

Свободная речь всё ещё должна быть извлечена в этот контракт. Локальная схема гарантирует форму извлечения, но сама по себе не гарантирует его смысловую полноту. Coverage использует ограниченный набор лексических маркеров и областей действия; этот аудит не доказывает распознавание любой перефразировки или любого дополнительного физического тезиса. Консервативное `incomplete` для неподдержанного или неполного ответа допустимо. В проверенных случаях неполное/неподдержанное содержание не превращается в положительный зачёт. В последнем узком прогоне D05 получает нейтральное уточнение; прежняя категоричная формулировка относится к предыдущему полному прогону.

В согласованном deterministic/API-наборе блокирующих замечаний не осталось. Общий pass пониманию произвольной речи и содержанию всех живых ответов не присваивается. Изменения после указанных хешей этим заключением не проверены.
